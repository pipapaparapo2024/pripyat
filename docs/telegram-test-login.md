# Telegram TEST: подготовка входа

## Актуальное состояние: вход включён, первый игровой тест опубликован

HTTPS `https://tg-test-pripyat-game.ru/` работает; меню `@pripyat_game_test_bot` открывает этот адрес. enabled=true. Игровой gateway и отдельный PHP-пул включены только в TG TEST. Вход → внутренний ID → сессия с request_key → загрузка игры → сохранение/повторный вход проверены по HTTPS и в headless браузере с искусственным host. Сам Telegram-клиент должен проверить пользователь. Детали выпуска и команд — в начале docs/CONTINUE_HERE.md. Старые записи ниже о выключенном входе/неподключённом API/невыданном HTTPS исторические.

БД создана по последующему явному разрешению пользователя: `stalker_telegram_test`, 15 таблиц. Актуальный SQL — `database/telegram-test-schema.sql`, отчёт — начало `docs/telegram-database-design.md`. Пароль отдельного ограниченного MySQL-пользователя записан в приватный конфиг, токен бота сохранён, вход остаётся enabled=false. Отметки ниже «БД не создана» относятся к предыдущим этапам.

Актуализация подключения домена: `@pripyat_game_test_bot` проверен через getMe без вывода токена, private config остаётся enabled=false. Включён отдельный HTTP nginx-vhost `tg-test-pripyat-game.ru`, заглушка отвечает 200 локально по Host. Конфигурации существующих сайтов и registry проверены по SHA256 без изменений; SQL не выполнялся. HTTPS НЕ выпущен: ns1.reg.ru отвечает A=155.212.211.202, но сервер зоны RU a.dns.ripn.net и публичные 1.1.1.1/8.8.8.8 пока возвращают NXDOMAIN. Let’s Encrypt отклонил проверку из-за DNS. После появления публичной делегации повторить `python tools/connect-telegram-test-domain.py`: certonly webroot затрагивает только новый сертификат, после успеха скрипт включает HTTPS/redirect только для этого vhost. Не считать домен готовым для Mini App до успешной публичной HTTPS-проверки.

Статус кода входа: подготовлен локально, не опубликован. БД не создана. Актуальное подключение домена/бота описано выше. Полный разбор предлагаемой схемы — `docs/telegram-database-design.md`; SQL авторизации не является полной игровой схемой.

Уточнение после регистрации домена: пользователь выбрал `tg-test-pripyat-game.ru`. На VPS подготовлены только `/var/www/stalker-tg-test/public/index.html` (заглушка), неактивный nginx-конфиг `/var/www/stalker-tg-test/config/nginx-http.conf` и закрытый конфиг `/etc/pripyat/telegram-test.php` (каталог 0700, файл 0600, root). Вход выключен, токен не внесён, сайт nginx не активирован, DNS/БД не менялись. Существующие private registry сверены без изменений. Повторяемый подготовительный скрипт `tools/prepare-telegram-test.py` сохраняет уже существующие файлы и не запускает SQL/nginx reload. Перед подключением отдельного PHP pool настроить его доступ к конфигурации; сейчас файл намеренно доступен только root.

## Что создаётся после согласования

1. Новая пустая БД `stalker_telegram_test`, отдельный MySQL-пользователь с доступом только к ней.
2. Игровые таблицы по `database/schema.sql`, без копирования строк игроков VK/OK. Это исходный снимок схемы: перед применением сверить с актуальной структурой, исключить исторические backup-таблицы и проверить наличие всех текущих игровых колонок. Пока этот снимок не считать окончательным установщиком Telegram-БД.
3. Две новые таблицы из `database/telegram-test-auth.proposed.sql`: `telegram_identities` и `telegram_sessions`. SQL не запускается кодом автоматически.
4. Приватная конфигурация вне document root по примеру `docs/telegram-config.example.php`, отдельный PHP pool с `PRIPYAT_TELEGRAM_CONFIG`, отдельный TEST-бот. Пример выключен.

`telegram_identities.player_id` — собственный AUTO_INCREMENT INT (в пределах совместимости текущих игровых таблиц). `telegram_id` — BIGINT UNSIGNED с UNIQUE; внешнее число не попадает в users.id. Создание связи, игрока и сессии выполняется одной транзакцией. Повторный вход не перезаписывает прогресс. Конкурентные первые входы сериализуются уникальным ключом и блокировкой строки. В базе хранится только SHA256 случайного токена; сессия живёт час. Очистку истёкших сессий добавить при развёртывании.

## Подготовленный контракт

POST `/server/telegram-login.php`, form-поле `init_data` из Telegram.WebApp.initData. Сервер проверяет HMAC SHA256, auth_date (10 минут, допуск будущего 30 секунд), уникальность полей и целочисленный ID. initDataUnsafe не является авторизацией. Невалидный вход отклоняется до подключения БД. Конфигурация только серверная, база строго stalker_telegram_test; клиент не выбирает окружение. Секреты и initData не логируются.

Ответ: platform=telegram, environment=test, player_id (строка внутреннего ID), token, expires_at. Клиентский модуль `_client/src/modules/telegram-login.js` возвращает сессию в памяти и разрешает только same-origin HTTPS endpoint.

Это первый этап авторизации, ещё не запуск всей игры. Текущий main/preloader и universal.php не переключены на Telegram: новый токен намеренно не принимается старым VK/OK API. Следующий этап — отдельный Telegram API gateway с проверкой сессии и серверным выбором БД, затем Telegram runtime и bootstrap игры. Нельзя подставлять новый токен в legacy secure или выдавать Telegram ID за vk_user_id. Перед включением игрового API необходим отдельный аудит Dev-whitelist: внутренний ID не должен давать права по совпадению с VK UID.

## Размещение

Покупать новый домен не требуется. HTTPS URL может использовать существующий домен и отдельный путь. Рекомендуются поддомены tg-test.pripyat-game.ru и tg.pripyat-game.ru с отдельными document root, PHP-конфигурацией, ботами и БД. Поддомены — рекомендация, ещё не настроены. TEST игры означает отдельного обычного бота для разработки; это не требует специальной тестовой сети Telegram.

## Проверки

`node tests/telegram-auth.test.js` исполняет PHP: подпись, чужой бот, истёкший/будущий запуск, дубликаты/битая кодировка, JSON, большие ID, запрет чужих БД/PROD, повторный вход, хеширование токена и откат ошибок на транзакционном fake store. `node tests/telegram-login-client.test.js` исполняет клиентский модуль. Реальный MySQL/конкурентность InnoDB и запуск из Telegram пока не проверены: новая БД не создавалась.

Источник протокола: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app

Локальная проверка 01.11.2026: полный npm test прошёл — 97 базовых проверок и 734 тестовых файла, 0 ошибок. PHP-синтаксис новых файлов проверен. Расширенная фикстура исполняет также реальный TelegramLoginStore с подменённым PDO: стартовые ресурсы, сохранность прогресса при повторном входе и откат трёх таблиц. Это не заменяет будущую проверку настоящего InnoDB после отдельного разрешения создать TEST-БД.
