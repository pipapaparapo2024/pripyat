## Граница мира

TEST: `stalker_telegram_test`. Будущая PROD: отдельная `stalker_telegram` (имя предложено). Для каждой собственные MySQL-пользователь, бот, секреты, сессии и конфигурация. У прикладного пользователя права только на свою БД; CREATE/ALTER/DROP не нужны работающей игре. Подключение выбирается серверной конфигурацией, не POST platform, Telegram ID, адресом страницы или параметром ссылки.

Одинаковый Telegram ID в TEST и PROD создаёт два независимых игровых аккаунта; их игровые ID могут совпадать численно и не обозначают общность прогресса. Никаких межбазовых JOIN, автоматической привязки к ВК/ОК или копирования строк игроков. Перенос релиза означает перенос кода и отдельно согласованных справочников, не TEST-данных в PROD.

## Состав первой игровой БД

Предлагается сохранить 10 игровых таблиц и добавить 5 Telegram-таблиц: всего 15 для запуска игры с друзьями и Dev-доступом. Для первого теста одного входа достаточно users + identities + sessions, но это не вся игровая схема. Ещё 2 таблицы платежей нужны на этапе Stars, итого предложенный полный состав первого платного выпуска — 17.

## Внутренний ID и жизненный цикл аккаунта

Не менять типы всех игровых ID ради Telegram: внешний Telegram ID хранится отдельно в BIGINT UNSIGNED и не передаётся как users.id. Оставляем игровой диапазон положительного signed INT до 2147483647 — это соответствует существующим users.id и PHP/SQL-связям. Нельзя независимо включать AUTO_INCREMENT и в users, и в identities.

Подготовленный вход выделяет ID в telegram_identities, затем создаёт users с тем же ID в одной транзакции, затем сессию. UNIQUE Telegram ID и блокировка строки сериализуют одновременные первые входы. Ошибка любого шага откатывает все изменения. Пропуски AUTO_INCREMENT после rollback допустимы. Повторный вход не выдаёт стартовые ресурсы снова и не сбрасывает ник/обучение/дату создания.

В текущем предложении identities выделяет ID раньше users, поэтому FK identities.player_id → users.id не добавлен. Предлагается обратный FK users.id → identities.player_id только после проверки совместимости reset/удаления; обязательной частью первого SQL его пока не делать. Для новых sessions/roles/friendships/invites FK к identities допустимы с RESTRICT, без массовых CASCADE. Удаление аккаунта — отдельная процедура, не очистка identities через Dev-reset.

Сброс прогресса должен сохранять связь Telegram ID с игровым ID, прекращать/обновлять сессии по выбранной политике и не терять историю реальных платежей. Таблицы идентичности и платежей нельзя включать в общую массовую очистку игровых таблиц.

## users: сохраняем текущую игровую модель

В users уже находятся валюты, уровень/опыт/сила, энергия и её анкер, инвентарь, оружие и lifetime-учёт, одежда/тату, навыки, достижения, прогресс локаций/базы, личные состояния боссов, мини-игры, разнарядка, хабар и его даты, обучение и настройки звука. Данные многих подсистем лежат в TEXT с JSON: не превращать перенос площадки в одновременную нормализацию всех этих полей.

Первый аккаунт получает ту же явную инициализацию, что текущая игра: exp=0, coins=10, cigarettes=1000, shmot=[], create_time и visit от серверного времени; остальные значения по согласованной игровой схеме. Стартовые energy/max_energy=50, level=1 уже заданы в локальном снимке. Ни стартового комплекта одежды, ни хабара, ни покупок/достижений из ВК/ОК не переносить.

Поля friends/friends_since при сохранении совместимости становятся только серверной проекцией Telegram-дружбы. friends_scope_granted — старое VK-разрешение, не источник Telegram-дружбы; не выставлять его фиктивно ради прохождения старого входа. votes_spent — историческое имя счётчика: перед Stars отдельно решить, какие именно задания/достижения он обслуживает; не смешивать голоса и Stars по числу. vk_params хранится в старой secure, а не в users: в Telegram оно не требуется.

Все поля даты/JSON оставить совместимыми на первом этапе. В частности, habar_bought_ts не округлять и не подменять, окончание хабара сохранять по текущему правилу МСК. Сроки сессий — Unix seconds; friends_since_ms — миллисекунды как фильтрация урона у боссов. Не менять единицы времени одновременно с переносом.

## Дружба и помощь

Для пары хранить одну каноническую запись: player_low < player_high, CHECK неравенства, уникальная пара. Это обеспечивает взаимность и запрещает самодружбу. Индекс по второму участнику нужен для списка друзей с обеих сторон. При повторном переходе по ссылке существующую friends_since_ms не обновлять.

При удалении удалить текущую связь; уже выданные награды и кулдауны качалки сохраняются. Повторное добавление создаёт новую дату; помощь боссам до этой даты не засчитывается. Текущий bosses.php опирается на friends/friends_since, поэтому нужен адаптер серверной проекции или изменение чтения именно в Telegram-ветке. Клиентские users.setFriendsCache и произвольный список users из запроса не должны менять каноническую TG-дружбу.

Качалка сейчас хранит отдельные направленные таймеры в users.gym_pump_cooldowns: A→B и B→A независимы, A→C независим. Сохранить JSON на первом этапе, не удалять таймер при удалении друга. Общение в чате не участвует в этих правилах. В invite-таблице нет inviter/invitee-статистики, счётчика привлечений и наград; она нужна лишь для определения владельца ссылки и её отзыва. Политику ротации/ограничений повторного добавления ещё согласовать.

## Сессии и права

Подготовленная telegram_sessions хранит SHA256 случайного токена, внутренний ID и expires_at; сырой токен только у клиента в памяти, бот-токен — только в приватной серверной конфигурации. initData не сохранять как долговечный пароль. Отдельный API gateway должен определить игрока по проверенной сессии, а не доверять posted uid.

В старом API secure дополнительно обеспечивает атомарную ротацию req_key. Новая таблица пока этого не реализует: до подключения игрового API нужно перенести соответствующую защиту (например поле request_key и compare-and-swap по сессии) либо спроектировать эквивалент. Выдача токена сама по себе не делает старый universal.php совместимым с Telegram.

Dev-whitelist жёстко задан в users.php; event.php имеет свой ADMIN_UIDS; top.php/users.php исключают конкретный VK UID из рейтингов. В Telegram все эти решения должны исходить из серверных ролей/настроек площадки. Нельзя автоматически выдавать права ID=1 или переносить четыре числа VK-whitelist. По умолчанию таблица ролей пустая. Внутренние ID не являются секретом.

## Общие состояния и начальные строки

В рулетке недостаточно создать пустую таблицу: код делает UPDATE WHERE id=1 и не создаёт строку при первом вращении. Нужен INSERT новой строки. Значения локального DDL: spin_counter=0, spin_threshold=3000, kush_counter=0, kush_threshold=6, keyring_owner_id=0, keyring_cycle_ends_at=0, jackpot_pool=3000. Это предлагаемая инициализация по существующим DEFAULT, не согласованное изменение экономики. Перед запуском отдельно подтвердить начальный пул/пороги; работающий мир ВК/ОК и его накопления не копировать. После настоящего попадания код выбирает следующий spin_threshold в диапазоне 3000–3500.

Лидеры зон начинают без владельцев/уважения, боссы — без боёв/урона/получений. Активное событие не переносить: только выключенное состояние. Подарочные ссылки и claims пустые; новые коды генерировать отдельно для Telegram. Одна кампания в нескольких площадках означает отдельные ссылки/учёт в каждой БД.

## Что не создавать и не переносить

- Все 10 таблиц с backup в имени: исторические снимки другого мира, не структура для запуска.
- secure: старые токены VK/OK и vk_params; Telegram использует собственные sessions.
- trans: старый VK-журнал с числовым tid, не подходящий общий реестр Stars.
- ok_payment_transactions: журнал callback ОК (его DDL есть в модели, но нет в локальном schema.sql).
- reward_admin_totp: секрет 2FA веб-админки; отдельная управляющая инфраструктура, не данные нового игрового мира. Не клонировать секреты. Многоплощадочную админку проектировать отдельно.
- Какие-либо реальные игроки, balances, friends, данные боёв, cooldown, наградные ссылки, журналы платежей, сессии и Dev-флаги из существующих БД.

## Stars: схема следующего этапа

Две таблицы разделяют заказ и факт начисления. Серверный заказ фиксирует товар, игрока, цену и состав награды на момент оформления. Callback должен находить этот заказ и проверять соответствие, а не принимать количество награды от клиента. Уникальный идентификатор платежа резервируется в той же транзакции, где блокируется игрок и начисляется награда. Повтор подтверждения не начисляет повторно; ошибка откатывает и запись, и начисление. Для возвратов сохранять историю, а не удалять запись оплаты.

Точные поля, длины идентификаторов и статусы согласовать при реализации по актуальному протоколу Telegram. Каталог Stars из пользовательского DOCX — источник цен; эта работа не меняет цены и не подставляет их из VK/OK. Бот-токен, webhook secret и ключи 2FA не хранить в этих таблицах.

## Справочники и развёртывание

Почти все игровые справочники сейчас в server/json и клиентских данных: уровни/товары/награды/боссы/локации. Их не нужно выдумывать как новые SQL-таблицы. Код и справочники можно выпускать общими версиями, а platform-specific цены и настройки — отдельными согласованными конфигурациями.

Перед подготовкой окончательного DDL нужна read-only сверка актуальной структуры со снимком: набор колонок users, индексы, движки, DEFAULT/NULL и все новые игровые таблицы. Локальный schema.sql содержит смешанные collations utf8mb4_unicode_ci и utf8mb4_0900_ai_ci, а OK-журнал уже отсутствует в снимке; импортировать весь файл без фильтра нельзя. Новые таблицы — InnoDB, utf8mb4, ASCII/binary collation для токенов и кодов. signed/unsigned должны совпадать там, где добавляются FK. Не добавлять сразу FK ко всем старым игровым таблицам: текущие reset-процедуры к этому не подготовлены.

Порядок после согласования: актуальная схема-only спецификация → создание новой БД и отдельных grants → 10 игровых таблиц без данных → identities/sessions/roles/friendships/invites → согласованные singleton seed → проверка схемы → отдельный Telegram API → тест нового входа и сохранения. Платёжные таблицы подключаются позднее. Для входа users может быть создана до identities, поскольку FK на users пока не предлагается. Ни одного ALTER в ВК/ОК не требуется.

Проверки после разрешения создать TEST-БД: первый/повторный/конкурентный вход; отказ чужого бота/истёкшего initData/подмены UID; rollback создания игрока; сохранение всех ресурсов и JSON; отсутствие Dev-прав у обычного ID; сохранение request-key защиты; взаимность/удаление/повтор дружбы; отсутствие старого урона; независимые 24ч качалки; стартовое состояние рулетки и зон; подарки только своей площадки; запрет credentials TEST к другим БД. Для Stars отдельно — duplicate callback, rollback начисления и возвраты. Сейчас эти MySQL-интеграционные проверки не исполнялись, поскольку создание БД не разрешено.
