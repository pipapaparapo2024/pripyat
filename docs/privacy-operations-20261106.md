## Подтверждённое обращение на удаление

Игрок обращается на почту поддержки. Для email-аккаунта — с привязанной почты; для ВК/ОК — подтвердить владение социальной учётной записью через штатный вход, а не скриншотом или знанием ID. Пароли не запрашивать. Оператор фиксирует номер обращения и проверяет точный мир. Удаление ВК/ОК-персонажа относится и к игре внутри этой соцсети. Остальные миры не затрагиваются.

На новом VPS:

```sh
php /usr/local/sbin/pripyat-privacy-admin --world=site --player=123
# Только после проверки владельца и конкретного поручения на удаление:
php /usr/local/sbin/pripyat-privacy-admin --world=site --player=123 --verified-ticket=REQUEST_20261106_001 --apply
```

`--world` только site/vk/ok; player — игровой ID этого мира, для ОК это launcher/game ID, не native OK ID. Номер обращения не должен содержать email или телефон. Первая команда — dry run. Реальные аккаунты для проверки команды не удалять.

Сначала создаётся независимая запись блокировки; затем под блокировкой персонажа удаляются прогресс, secure, рейтинги, вклад в боссов, заявки, присутствие в чужих списках друзей и последнем победителе рулетки. Чужие балансы и экземпляры боссов сохраняются. Для сайта удаляются телефон/почтовые токены/сессии/приглашения и аватар. Для соцсетей — профильные кэши, динамические привязки, относящиеся к ним challenge/диагностика/сессии. Аккаунт соцсети у провайдера не удаляется.

Незавершённый платёж останавливает SQL-удаление; аккаунт остаётся заблокированным, оператор сначала разбирает платёж, затем повторяет команду. При наличии финансовой истории сохраняется обезличенная служебная строка site_accounts для внешних ключей (deleted.invalid, нерабочий пароль, disabled_at). Платежи/квитанции/учётные записи trans не удаляются этой процедурой. Юридические сроки финансового учёта и состав обязательных документов должен утвердить оператор с бухгалтером; автоматического удаления финансовой истории нет. Не заявлять, что все сведения исчезают без исключений.

Журнал `/var/lib/pripyat-privacy/deletions.json`, root 0600, хранит минимальный ID/мир/даты/хеш номера обращения/результат. Рабочая deny-проекция в `/tmp/pripyat-privacy/erased-accounts.json` проверяется сервером на каждом входе/запросе native и site-сессии. Нельзя удалять этот журнал вместе с восстановлением SQL. Он копируется отдельно на компьютер. При отсутствии guard HTTP-вход закрывается. Сервис восстановления guard запускается после MySQL при загрузке системы до FPM, затем каждый час.

## Сроки

Аккаунт/телефон/аватар/прогресс — до подтверждённого удаления, без удаления за неактивность. Email/phone-check — очищаются через 6 суток после expires_at ежечасно (публичный предел 7 суток после истечения). Диагностика/лимиты — 6 суток + максимум час. Challenge — сутки с обновления + максимум час. Файлы PHP-сессий и DB site_sessions — сутки после истечения + максимум час (публичный предел 48 часов). Действующие сессии не удаляются по одному старому mtime. Минимальный журнал удалений — 3 года для подтверждения и предотвращения восстановления; нерешённые ошибки удерживаются до устранения.

Архивы SQL и распознанные снимки приложения — 30 дней с ежечасной очисткой. На выключенном компьютере удалить файл физически невозможно: локальная очистка выполняется при ручном запуске. Это ограничение явно отражено на сайте. Системные журналы PHP-FPM/journald не следует приравнивать к журналам игрового приложения: общая система имеет собственную ротацию. Нельзя обещать один срок для абсолютно всех логов.

## Восстановление без возврата удалённых аккаунтов

1. Закрыть вход на восстанавливаемом окружении. Проверить SHA256 и gzip выбранных архивов; отвергнуть старше 30 дней.
2. Найти наиболее актуальный независимый `deletions-current.json` с компьютера/сохранившегося VPS. Он важнее журнальной копии внутри старого снимка. Если журнал утрачен/устарел, не объявлять восстановление безопасным и не открывать игру, пока оператор не сверит последующие обращения.
3. Восстановить SQL в закрытом окружении. Не восстанавливать старый `/tmp` guard или старые PHP-сессии. Остановить прикладные записи на время операции.
4. Загрузить независимый журнал на сервер root 0600 и выполнить:

```sh
python3 /usr/local/sbin/pripyat-privacy-import-ledger.py /root/deletions-current.json
systemctl start pripyat-privacy-maintenance.service
```

5. Проверить успешный сервис, отсутствие удалённых персонажей, блокировку их старых ID и работу обычного пользователя. Только затем открыть вход. Полное восстановление ОС требует установить privacy-guard и сервисы заново до открытия HTTP.

Обновлять локальную копию журнала сразу после обработанного обращения. Ежедневная копия может не знать об удалении, сделанном позже; это не автоматическая репликация.
