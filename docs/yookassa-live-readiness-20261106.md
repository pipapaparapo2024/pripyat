# ЮKassa: подготовка боевого режима 06.11.2026

Позднейшее изменение по отдельному разрешению владельца: включены реальные покупки только разработчикам с временными ручными чеками. Актуальные режим, проверки и первая подтверждённая настоящая оплата описаны в docs/developer-live-payments-20261106.md. Ниже сохранён отчёт предыдущего этапа подготовки.

По последнему решению владельца реальные покупки остаются закрытыми до подключения автоматических чеков НПД. Не включать их на основании наличия ключа или одобренной модерации.

## Что проверено и опубликовано

- Настоящий GET /v3/me: HTTP 200, account_id 1517337, test=false, status=enabled. Платежи не создавались.
- Адаптер поддерживает два явно заданных режима. Префикс ключа должен соответствовать режиму; сумма, RUB, магазин, ID платежа, ID заказа и игровой мир проверяются по ответу API.
- Боевые намерения покупки получают отдельные ID, зависящие от магазина. Старый тестовый заказ нельзя случайно переиспользовать как боевой.
- Серверные status/webhook могут найти старый платёж через прежние настроенные реквизиты. Параметры уведомления не выбирают магазин. Переключение на предыдущий магазин допускается только при ответе API 404, а не при сетевой ошибке.
- Для нового реального заказа одновременно нужны live_checkout_enabled=true и receipt_automation_ready=true. Эти флаги сейчас false. Они являются блокировкой запуска, а не реализацией чеков.
- Активная payments-конфигурация остаётся тестовой. Боевые реквизиты подготовлены в payments_live, прежние тестовые — в payments_previous приватного runtime. Списки допущенных тестировщиков сохранены.
- Публикация только шести PHP-файлов сайта; native-клиент, обработчики платежей ВК/ОК и их приватная конфигурация сверены без изменений. БД не мигрировались, службы не перезапускались.
- Backup: /var/backups/yookassa-live-ready-20261106T191333Z.

## Что ещё требуется перед реальной оплатой

Выбрать и подключить сервис чеков НПД, проверить выдачу и доставку чека, ошибки/повторы и возвраты. Владелец подтвердил сохранение в боевом магазине HTTP-уведомлений payment.succeeded и payment.canceled на https://pripyat-game-site.ru/server/site-payments-webhook.php. Сохранение этих настроек не включает покупки само по себе.

Дополнительная проверка: наш обработчик принимает POST с неподдерживаемым диагностическим событием и возвращает HTTP 200 без начислений. Получение настроек кабинета через GET /v3/webhooks с Basic Auth недоступно: HTTP 401, Authentication type is not allowed. По официальной документации этот API предназначен для OAuth; это не ошибка сохранённого боевого ключа (GET /v3/me ранее прошёл). Сами галочки кабинета и доставку реального уведомления этим запросом не проверили. Реальные покупки по-прежнему закрыты.

После готовности чеков переключить active payments на подготовленную боевую конфигурацию, сохранив историю тестового магазина. Только затем отдельно согласовать и провести минимальную настоящую оплату и сверить начисление/чек. Реальная оплата этим релизом не проверена.

## IP и VPN

Проверены Nginx, UFW, iptables/ip6tables и nftables: правил GeoIP/стран нет; 80/443 доступны всем IPv4/IPv6. Семь deny all защищают служебные/скрытые файлы и локальную health-проверку. Единственный jail Fail2ban — sshd, только TCP 22: на момент проверки 0 активных банов, 14 исторических. Это не аудит внешней сети провайдера и не доказательство доступности из каждой страны.

На компьютере владельца запрос к https://pripyat-game.ru/client/ver0_41/ напрямую: HTTP 200, 0.177 секунды. Через текущий локальный HTTP-прокси 127.0.0.1:10809 туннель CONNECT отвечает 200, затем TLS не завершается за 5 секунд. Это воспроизведение сбоя пути через прокси до загрузки документа, а не установленная причина на конкретной стороне. Настройки VPN/прокси/firewall не менялись.

Регистрация самостоятельных аккаунтов по-прежнему требует поддерживаемого российского мобильного номера. Это отдельное ограничение, не IP-блокировка; казахстанские +77 номера текущий нормализатор не принимает.
